pando

One repo. Every branch alive.

pando runs every branch you are working on at the same time, each with its own checkout, ports, logs and, if you want, database. It all fits on one terminal screen, and nothing is written into your repository.

$brew install mertkaradayi/tap/pando

It looks like a forest. It is one tree.

Pando is a grove of quaking aspen. Its roughly 47,000 trunks all grow from a single root system, which makes it one living thing, and the heaviest known on Earth.

  • 47,000trunks, roughly
  • 1root system under all of them
  • Heaviestknown living thing on Earth
  • “I spread”what its name means in Latin

Your repository grows the same way.

Git can check out many branches side by side, each in its own folder, all sharing one history: worktrees. The repository is the root. Every branch can be a trunk.

  • Root→your repository: one .git, one history
  • Trunk→a branch, in a worktree of its own

But in one checkout, branches take turns.

To look at another branch, you stash, switch, reinstall and restart, and the port is still taken. Its migrations land in your database. Then you do it all again to come back.

One checkout

$ git stash
$ git switch fix/login
$ pnpm install
$ pnpm dev
Error: listen EADDRINUSE :::3000

Branches take turns, and showing a teammate means staging first.

pando lets every branch run at once.

$ pando new fix/login
$ pando start fix/login
$ pando ls
NAME       STATUS   URL
main       running  http://localhost:20177
feat/cart  running  http://localhost:23001
fix/login  running  http://localhost:23249

Each branch gets a checkout of its own, already running, on its own ports. You see all of them on one screen.

Every key and what it does

How it works

Three commands. A branch, running.

pando builds on git worktree, the side-by-side checkouts git has had since version 2.5. It adds everything that makes each one run.

How a worktree is made, step by step
  1. 1

    Its own checkout.

    A real git worktree in pando’s own folder, with your .env linked in and its dependencies installed. Your main checkout is untouched.

    $pando new feat/checkout
  2. 2

    Its own ports.

    Every process starts in the background, on ports no other branch uses, kept across restarts. pando waits until each is ready.

    $pando start feat/checkout
  3. 3

    Its own URL.

    It opens in your browser, and pando share gives a teammate a public link.

    $pando open feat/checkout

It keeps running.

Close the terminal or quit pando, and your servers stay up. No daemon.

Environment, never files.

Ports and addresses reach your app as environment variables. pando never edits a .env or a config file.

Your main checkout too.

Always the first row. pando runs its processes on ports it gives them, nothing more.

Worktrees made by hand.

Every worktree git knows about is listed and run. pando adds no file to one it did not make.

Every process also gets PANDO_NAME, PANDO_BRANCH, PANDO_WORKTREE, PANDO_ROOT and PANDO_PROJECT; what pando check runs also gets PANDO_CHECK=1, and a namespaced worktree's get PANDO_NAMESPACE.

Light on disk

A whole checkout, for the price of what changed.

Where the disk can clone (APFS on macOS; btrfs, XFS or bcachefs on Linux), a new worktree’s files are copy-on-write clones of your main checkout’s, so git writes only what your branch changed.

du still counts each worktree in full. The saving shows up as free space.

Copy-on-write, clone and the disk report

  • Dependencies, cloned.

    clone gives a new worktree your main checkout’s node_modules before the install, so the install fixes only what differs.

  • Rust builds, cloned.

    clone can take a crate’s target too, so a branch compiles only its own crates.

  • Measured, not guessed.

    A passing pando check reports what a worktree costs on disk and what could still be shared. What to share is your call.

Data

Its own database, if you want one.

Code, ports and logs always belong to the worktree. You choose where its data lives, branch by branch.

The three modes in full

Shared Default

S·--shared

It uses your main checkout’s database and cache. Nothing to start, nothing to wait for: right for most changes.

Namespaced Experimental

⏎ then choose·--namespaced

A database of its own inside the server you already run: shop__feat_x next to shop, or a Redis slot next to slot 0. The branch’s migrations build it; main’s data is never touched.

Isolated

i·--isolated

Servers of its own, on ports of its own: your compose file’s containers, or native Postgres, MariaDB, Redis or MongoDB without Docker.

One key to choose.

Press ⏎ on any worktree to pick a mode, or to switch one that is running. pando remembers your choice.

How does the app find its database?

Through its environment: pando takes the address your .env has and changes only the port, the database name or the slot.

Namespaced mode is opt-in and careful: every name it makes begins with your main database’s name, and pando rm drops only what pando’s records say it made.

What it reads.

Your lockfile, scripts, env example, version files and compose file. Every decision lands in ~/.pando, with its reason.

Two promises

Your repository stays yours.

These two rules come before every feature.

How the promises are kept

Promise 1

pando never writes into your repository.

No config file, no gitignore line, no lockfile change. Everything pando learns and runs lives in ~/.pando, and its tests check that git status stays clean.

~/.pando/
├── config.toml
└── projects/acme-shop-2bdf70d7/
    ├── pando.toml
    ├── state.json
    ├── worktrees/feat+login/
    ├── logs/feat+login/
    └── data/feat+login/

~/code/acme-shop/   untouched

Promise 2

No AI at runtime.

An agent may help set pando up. Starting, stopping, sharing and removing only read a file you can edit, so a wrong guess costs one edit, never a mystery. No telemetry, no account.

Two things you choose reach past this rule, each with rules of its own: namespaced mode makes databases in your own server, and the git menu moves a branch after showing you its commands.

And more

Everything around a branch.

One screen for all of it, for you and for the agents working beside you.

Share a branch

pando share puts a running worktree on a public URL. No account.

Pull requests, running

Press p, pick an open pull request, press ⏎: it becomes a worktree, even from a fork.

A careful git menu

Fetch, pull, rebase or merge, the exact commands shown first. Conflicts abort; nothing is pushed.

Several repositories, one project

Run pando in a folder of sibling repositories: one branch spans them all, in one row.

Many at once

pando rm feat/a feat/b removes both, and start and stop take several names. On screen, mark rows with +.

Keyboard first, mouse too

Every action has a key. Click a row, click again to open it, scroll anywhere.

A real log viewer

A tab per process and one for all, search, a level filter, and a jump from error to error.

Built for agents

Listings come as JSON, and exit code 3 means pando has a question.

macOS and Linux, and Windows inside WSL 2, where pando open opens Windows’ browser.

Install

Install it. Run it in your project.

A ready-made binary for macOS (Apple silicon and Intel) and Linux (x86_64 and arm64), and inside WSL 2 on Windows. No Rust needed.

Homebrew

$brew install mertkaradayi/tap/pando

On macOS and Linux, WSL 2 included.

Install script

$curl --proto '=https' --tlsv1.2 -LsSf https://github.com/mertkaradayi/pando/releases/latest/download/pando-cli-installer.sh | sh

This puts pando in ~/.local/bin, or $XDG_BIN_HOME when that is set, and adds that folder to your PATH. Set PANDO_CLI_NO_MODIFY_PATH=1 to leave your shell files alone.

From source

$cargo install --locked --git https://github.com/mertkaradayi/pando pando-cli

This needs Rust 1.88 or newer, which rustup installs.

Then run it

The first time, pando opens the setup screen. After that, every branch on one screen.

$ cd your-project
$ pando

Keep it current

This upgrades pando the way you installed it.

$pando update

Every download has a checksum and a GitHub attestation. pando doctor names anything your project still needs; pando never installs anything itself.

Where it stands

pando is pre-release. It is used daily on the monorepo it was built for, and every change is tested on macOS and Linux. It has met only a handful of real projects. If it breaks on yours, that is the most useful issue you can open.
