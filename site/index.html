Every key and what it does

Fishlake National Forest, Utah

It looks like a forest. It is one tree.

Pando is a grove of quaking aspen. Walk through it and you count trees; dig, and you find only one.

  • 47,000trunks, roughly
  • 1root system under all of them
  • Heaviestknown living thing on Earth
  • “I spread”what its name means in Latin

Your repository grows the same way.

Git can check out many branches side by side, each in its own folder, all sharing one history: worktrees.

  • Root→your repository: one .git, one history
  • Trunk→a branch, in a worktree of its own

How it works

Three commands. A branch, running.

How a worktree is made, step by step
  1. 1

    Its own checkout.

    A real git worktree, with your .env linked in and dependencies installed.

    $pando new feat/checkout
  2. 2

    Its own ports.

    Processes run in the background on ports no other branch uses. Quit pando and they keep running.

    $pando start feat/checkout
  3. 3

    Its own URL.

    It keeps its address across restarts and opens in your browser.

    $pando open feat/checkout

Light on disk

A whole checkout, for the price of what changed.

Where the disk can clone (APFS on macOS; btrfs, XFS or bcachefs on Linux), a new worktree’s files are copy-on-write clones of your main checkout’s. clone does the same for node_modules or a Rust target.

Copy-on-write, clone and the disk report

Data

Its own database, if you want one.

The three modes in full

Shared Default

S·--shared

It uses your main checkout’s database and cache. Nothing to start, nothing to wait for: right for most changes.

Namespaced Experimental

⏎ then choose·--namespaced

A database of its own in the server you already run: shop__feat_x next to shop. The branch’s migrations build it; main’s data is never touched.

Isolated

i·--isolated

Servers of its own, on ports of its own: your compose file’s containers, or native Postgres, MariaDB, Redis or MongoDB without Docker.

Your app finds its database through its environment: pando takes the address in your .env and changes only the port, the database name or the slot.

Two promises

Your repository stays yours.

How the promises are kept

Promise 1

pando never writes into your repository.

No config file, no gitignore line, no lockfile change. Everything pando learns and runs lives in ~/.pando, and its tests check that git status stays clean.

Three things fall outside it by design, each with rules of its own: namespaced mode, the git menu and the copy-on-write checkout.

~/.pando/projects/acme-shop-2bdf70d7/
├── pando.toml
├── worktrees/feat+login/
├── logs/feat+login/
└── data/feat+login/

~/code/acme-shop/   untouched

Promise 2

No AI at runtime.

An agent may help set pando up, but what pando runs comes from rules and a file you can edit, never a model. A wrong guess costs one edit, never a mystery. No telemetry, no account.

And more

Everything around a branch.

Pull requests, running

Press p, pick an open pull request, press ⏎: it becomes a worktree, even from a fork.

Share a branch

pando share puts a running worktree on a public URL. No account.

A real log viewer

A tab per process and one for all, search, a level filter, and a jump from error to error.

A careful git menu

Install

Install it. Run it in your project.

A ready-made binary for macOS and Linux, x86_64 or ARM, and for WSL 2 on Windows.

Homebrew

$brew install mertkaradayi/tap/pando

Install script

$curl --proto '=https' --tlsv1.2 -LsSf https://github.com/mertkaradayi/pando/releases/latest/download/pando-cli-installer.sh | sh

It puts pando in ~/.local/bin, or $XDG_BIN_HOME when that is set, and adds it to your PATH. PANDO_CLI_NO_MODIFY_PATH=1 leaves your shell files alone.

From source

$cargo install --locked --git https://github.com/mertkaradayi/pando pando-cli

This needs Rust 1.88 or newer, which rustup installs.

Then, in your project

$pando

Later, to update it

$pando update

pando is pre-release. If it breaks on your project, open an issue. Where it stands
