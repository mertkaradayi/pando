pando

One repo. Every branch alive.

Every branch you are working on, running at once: each in its own checkout, on its own ports, with its own logs and, if you want, its own database. All on one terminal screen.

Fishlake National Forest, Utah

›It looks like a forest.
It is one tree.

Pando is a grove of quaking aspen. Its roughly 47,000 trunks all grow from one root system, which makes it a single living thing, and the heaviest known on Earth. Its name is Latin for “I spread”.

trunk → branch · root → repository

›Your repository grows the same way.

Git can check out many branches side by side, each in a folder of its own, all sharing one history. Git calls these checkouts worktrees. Your repository is the root; every branch can be a trunk.

one checkout · one port 3000 · one branch at a time

›But in one checkout,
branches take turns.

To look at another branch you stash, switch, reinstall and restart, and the port is still taken. Its migrations land in the database you were using. To show a teammate, it goes to staging first. Then you do it all again to come back.

so I built pando, for my own work first · Mert Karadayi

›pando lets every branch run at once.

Each branch you work on gets a checkout of its own, already running, on ports no other branch uses. You see all of them on one screen, and switching branches stops being a chore.

›Three commands.
A branch, running.

pando drives git worktree, the side-by-side checkouts git has had since 2.5, and adds everything that makes each one run

// pando’s own output, trimmed; the ports are examples

It keeps running

Close the terminal or quit pando, and your servers stay up. There is no daemon to look after: pando reads what runs from its own records each time.

Environment, never files

Ports and addresses reach your app as environment variables, such as PORT and DATABASE_URL. pando never edits a .env or a config file to set them.

Your main checkout too ⌂

It is always the first row, and it runs like the others. Since it is yours, pando only runs its processes on ports it gives them: no install, no hooks.

Worktrees you made by hand

pando lists every worktree git knows about, and starts and stops them the same way, without writing into them.

›A whole checkout, for the price of what changed.

copy-on-write worktrees · clone · measured by pando check

You keep many worktrees, so what one costs is paid many times over. Under each trunk below are its files on disk.

On a disk that cannot clone, such as ext4, pando uses git’s own checkout. du still counts each worktree in full; the saving shows up as free space. What to share is your project’s call: pando measures, and proposes clone for the node_modules or Rust target your main checkout has, but not where the install deletes it first, as npm ci does.

›Its own database, if you want one.

code, ports and logs always belong to the worktree · you choose where its data lives, branch by branch

Press ⏎ on a worktree to pick its mode, or to switch one that is running. pando remembers the choice: a plain start keeps the mode it last ran in. The main checkout has one mode, its project’s own services, so ⏎ there starts it at once.

How does the app find its database?

Through its environment. pando reads the address your .env already has and changes only what the mode needs: the port, the database name or the slot. Your app needs no code for pando, and no file is written to tell it.

Namespaced mode works inside a server you own, so it is careful. It is opt-in. Every database it makes is named after your main one (shop__…), so it can never be your main database. It takes a Redis slot only while the slot is empty, and pando rm drops only what pando’s own records say it made.

›Everything around a branch.

one screen for all of it, for you and for the agents working beside you

Several repositories, one project

A product split across repositories cloned side by side is one project: run pando in the folder that holds them. One branch then spans all of them, in one row, and one start runs every process in one port window, so the frontend is told the backend’s port.

Several repositories in full →

Share a branch, no staging

pando share, or t in the screen, puts a running worktree on a public https link through a Cloudflare quick tunnel. A teammate opens your branch on their phone without anything being deployed, and no account is needed.

Public means public: anyone with the link reaches the app until you unshare, stop, restart or remove the worktree, so the screen asks first. If your app needs a login, auth_cmd can open the link already logged in. Sharing in full →

A teammate’s pull request, running

Press p for the repository’s open pull requests, type to narrow them, and press ⏎. The pull request becomes a worktree you can start, even when it comes from a fork. Reviewing stops meaning “stash my work and check out theirs”.

A row with a pull request shows ◍ #128, and space p opens it on GitHub. It uses the GitHub CLI, gh, signed in. Pull requests in full →

A careful git menu

space g on a row says where its branch stands against its base, then offers to fetch, pull, rebase or merge the base in. Every move shows its exact git commands before ⏎ runs them.

A rebase or merge that hits a conflict is aborted, so the checkout ends as it was. It never pushes, resets, stashes or switches branches, and with uncommitted changes it only fetches. The git menu →

Many at once

start, stop, restart and rm take several names and act on them side by side, each reported as it finishes. On screen, + marks rows, and s x r d then act on every marked one at once.

On screen, removing several asks once, in one dialog that says what each removal stops or takes with it. A worktree with uncommitted changes is only removed when you say so: F in that dialog, --force on the command line. Several at once →

  2. Copy one line. Press a and paste it into Claude Code or Codex, opened in the same project.
    Set up pando here: run `pando init --agent` and follow what it says.
  3. Your agent does the rest. It reads what pando found, settles what is left open and writes its answers through pando, never into your repository. It asks you nothing, and tells you what it set.
  4. pando check proves it. A throwaway worktree is installed, started, asked for its first page and removed. When it passes, the screen turns green.

No agent? Or no setup?

Press ⏎ on the setup screen and pando makes its own guess, tested by the same check. Press esc to skip setup and only manage worktrees; nothing waits on it.

What it reads

Your lockfile, dev scripts, env example, version files and compose file. It knows Next.js, Vite, Nuxt, Astro, Angular, Expo, Django, Rails, Phoenix and Laravel, as well as plain Node, Go and Rust projects. Every decision lands in ~/.pando, with its reason, and you can edit any of it.

›Your repository stays yours.

two rules come before every feature

invariant 1

pando never writes into your repository.

No config file, no gitignore line, no lockfile change. Everything pando learns and runs lives in ~/.pando, and its tests run every command and then check that git status has nothing to report.

~/.pando/
└── projects/acme-shop-2bdf70d7/
    ├── pando.toml             the project’s config
    ├── worktrees/feat+login/  the branch’s checkout
    ├── logs/feat+login/
    └── data/feat+login/

~/code/acme-shop/             untouched

invariant 2

No AI at runtime.

An agent may help set pando up. Starting, stopping, sharing and removing only read a plain file you can edit, so a wrong guess costs you one edit and never a mystery. There is no telemetry, and you need no account.

  1. detectionrules, never a model
  2. pando.tomla file you can read and edit
  3. start · stop · share · rmdo what that file says

Where it reaches further, by your choice. A namespaced worktree’s database lives in your own server, under a name built from your main database’s, and only pando rm drops it. The git menu moves a branch only when you pick the move and have seen its commands. A copy-on-write checkout writes the branch’s own tracked files into the worktree it just made, as git worktree add would.

›Install it. Run it.

a ready-made binary for macOS and Linux, Intel or ARM · on Windows, inside WSL 2 · no Rust needed

  1. 1Install
    $ brew install mertkaradayi/tap/pando
    $ curl --proto '=https' --tlsv1.2 -LsSf https://github.com/mertkaradayi/pando/releases/latest/download/pando-cli-installer.sh | sh

    It puts pando in $XDG_BIN_HOME when that is set, otherwise usually in ~/.local/bin, and adds it to your PATH. PANDO_CLI_NO_MODIFY_PATH=1 leaves your shell files alone.

    $ cargo install --locked --git https://github.com/mertkaradayi/pando pando-cli

    This needs Rust 1.88 or newer, which rustup installs.

  2. 2Run it in your project
    $ cd your-project
$ pando

    The first time, pando opens the setup screen. After that, it shows every branch on one screen.

  3. 3Keep it current
    $ pando update

    It upgrades pando the way you installed it.

Every download has a checksum and a GitHub attestation. pando doctor lists anything your project needs that is missing, such as Docker for isolated services, cloudflared for sharing or gh for pull requests, with the command that installs it. pando never installs anything by itself.

where it stands, honestly

pando is pre-release. It is used daily on the monorepo it was built for, and every change is tested on macOS and Linux, but it has met only a handful of real projects. If it breaks on yours, that is the most useful issue you can open.
