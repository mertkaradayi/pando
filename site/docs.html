Install

pando ships a ready-made binary for macOS (Apple silicon and Intel) and Linux (x86_64 and arm64). Homebrew and the install script need no Rust. On Windows it runs inside WSL 2 as the Linux binary: see Platforms.

With Homebrew

On macOS or Linux, WSL 2 included:

$brew install mertkaradayi/tap/pando

With the install script

With nothing else installed, this one line does the same:

$curl --proto '=https' --tlsv1.2 -LsSf https://github.com/mertkaradayi/pando/releases/latest/download/pando-cli-installer.sh | sh

The script puts pando in $XDG_BIN_HOME when that is set, and otherwise usually in ~/.local/bin, and adds that directory to your PATH in your shell's startup files. To leave those files alone, run it with PANDO_CLI_NO_MODIFY_PATH=1 set. Running the line again later installs the newest release.

From source

Building pando yourself needs Rust 1.88 or newer. With no Rust on the machine, rustup installs the current stable toolchain first, and a new terminal then has cargo:

$ curl --proto '=https' --tlsv1.2 -sSf https://sh.rustup.rs | sh
$ cargo install --locked --git https://github.com/mertkaradayi/pando pando-cli

--locked builds with the exact dependency versions CI tested. Without it, cargo may pick newer ones that need a newer Rust. On a new Mac, git comes with the Xcode Command Line Tools (xcode-select --install).

There is no crate on crates.io yet.

Checksums and attestations

Every download has a checksum and a GitHub attestation. To prove a file was built from this repository, run gh attestation verify <file> -R mertkaradayi/pando.

Staying current

$pando update

It updates pando to the latest release the same way it was installed, and leaves your shell's files alone:

pando --version says which version you have. pando update --check says whether a newer release is out and which command would install it, and runs nothing. What changed in each release is in the changelog.

Shell completions

pando completions zsh prints a completion script, and so does the same command for bash, fish, elvish or PowerShell. In bash, zsh and fish it completes worktree names too.

Trying it on a fixture first

Want to see pando before you point it at your own project? In a clone of pando's repository, with Rust installed, the test suite can build repositories of every shape it knows. One of them is a good place to start:

# the shapes the tests use
$ scripts/fixture-repo.sh --list

# build one in a temporary directory, and print how to run pando in it
$ scripts/fixture-repo.sh mono-web-api --listener

Your first run

Open a terminal in a git repository you work on, the one with the dev server you wish you could run on two branches at once, and run pando:

$ cd your-project
$ pando

There is nothing to configure first, and what pando learns about the project is kept in ~/.pando, outside your repository. The first time, in a project with nothing to run yet, pando opens its setup screen instead of the list.

The setup screen

The screen is drawn over a grove grown from your project's name, whose roots light up when the setup passes. Every project is a little different, so the surest start is to let your own coding agent look at it:

  1. Copy one line. Press a to copy this prompt:
    Set up pando here: run `pando init --agent` and follow what it says.
  2. Paste it into your agent. Claude Code or Codex, opened in the same project.
  3. Come back. The screen turns green by itself when the setup is done. From then on, pando opens the list.

What your agent does

pando init --agent prints the job for this project and this version of pando: what pando already sees, the questions still open, and the steps. Your agent then:

  • Decides what pando's rules leave open, from the project's own evidence, and asks you nothing.
  • Answers through pando, with pando init --answers - on stdin, never a file in your repository. --dry-run previews, and --replace corrects an answer.
  • Proves it with pando check: a throwaway worktree, installed, started, asked for its first page, and removed.
  • Reports what it set, why, how to change it, and what one worktree costs on disk. It never ends on a question.

It can also remember how to run the project with pando, in its own memory, if you say so.

No agent, or no setup

No agent? Press ⏎ on the setup screen and pando tries its own guess, tested by the same pando check. Press esc to skip the setup and go straight to the list. Nothing is ever gated on it, and the screen is not shown again. A project configured before the setup screen existed is never sent there.

pando new and pando start work on a project that was never set up, too: they take pando's first choice and say so.

Your first worktree

Work on a second branch next to the first:

$ pando new feat/checkout     # its own checkout, dependencies installed
$ pando start feat/checkout   # its own dev server, on ports of its own
$ pando open feat/checkout    # in your browser

Your main checkout is untouched and still runs as before. In the TUI: n, type the branch, ⏎ to make it; ⏎ on its row to pick a mode and start; o to open. pando rm feat/checkout stops the worktree and removes the checkout and its data. The branch stays.

Then run pando doctor to see which tools the project will need.

pando itself is one binary. Only git is required. Platforms

macOS

pando is developed on macOS, on Apple silicon and Intel. On APFS, a new worktree is a copy-on-write clone of your main checkout (see Light on disk).

Linux

Binaries ship for x86_64 and arm64. CI runs the whole test suite on Linux for every change, and it must pass, but nobody has used pando on Linux for real work yet. Copy-on-write works on btrfs, XFS and bcachefs. On ext4, which cannot clone, pando uses git's own checkout.

Windows, with WSL 2

On Windows, pando runs inside WSL 2 as the Linux binary. Install it in your distro any of the ways under Install.

  • Keep the repository under ~ in WSL, not on /mnt/c. git is several times slower on a Windows drive, and an edit there sends no file event, so dev servers never reload.
  • Install your tools inside WSL too, Node and Docker among them. For Docker, turn on Docker Desktop's WSL integration. pando doctor says when the shell finds Windows' copy of a tool instead, or when the repository sits on a Windows drive.
  • URLs work from Windows. A worktree's localhost URL opens in Windows' browser, and pando open opens it there (through wslview, then rundll32.exe, then xdg-open). The TUI copies through clip.exe.

A native Windows build compiles, but it runs nothing yet except completions: starting and stopping processes is written for Unix only so far. It says to use WSL 2.

Expo and mobile apps

pando recognises Expo apps. Metro, Expo's bundler, is a process no browser opens (page = false), so it is never a worktree's URL.

Instead, pando open and the TUI's o open the app: on the booted iOS simulator, else on a connected Android device or emulator, else on a simulator pando starts, on a Mac with Xcode. With none of those, it prints the commands.

pando status gives each app's links. When a branch changed native code, it names the changes and gives the build command Expo accepts, such as npx expo run:ios --port <port>. It also says when the build on the simulator is for another SDK.

Worktrees

pando does not invent a new kind of checkout. It drives git worktree, the side-by-side checkouts git has had since version 2.5, and keeps everything around them in its own home, ~/.pando: the ports, the processes, the logs, the private services, and the record of what runs where.

A worktree is an ordinary directory on a branch of its own: cd into it, open it in your editor, commit from it. Every worktree shares the repository's one .git, so a commit made in one is visible from all of them at once.

Names

A worktree is named by its branch, feat/login, or by its directory, feat+login. A slash cannot be in a directory name, so it becomes a plus. Every command takes either spelling.

Inside a worktree, start, stop, restart, logs, open, share and unshare need no name at all: they act on the worktree you are in.

What pando new does

  1. Finds the branch. A local branch is checked out as it is. Otherwise pando looks for it on origin, and fetches it if it is missing, never prompting for a password. Otherwise it makes a new branch, forked from the base (see below).
  2. Checks it out. It runs git worktree add into ~/.pando/projects/<id>/worktrees/feat+login. The project id is the checkout's directory name and eight hex characters of a hash of its path. Where the disk can clone, the files are copy-on-write clones of your main checkout's, and git writes only what the branch changed: see Light on disk.
  3. Provisions. The gitignored files you listed in provision, such as .env, are linked in from the main checkout. They are symlinks by default, so editing one edits main's. provision_mode = "copy" gives each worktree its own copy. A path the project does not gitignore is refused.
  4. Installs. The project's install step, such as pnpm install --frozen-lockfile, runs in the new worktree, so its dependencies are its own. The paths in clone, such as node_modules, are cloned in first, so the install only fixes what differs.

A new branch forks from the first of these that applies:

  1. --base
  2. a matching glob in [branches] rules
  3. [project] base
  4. origin/HEAD, then main, then master

It forks from the last-fetched commit, so run git fetch first when you need the newest.

A worktree made before provision was answered, or one that lost a file since, gets the file at its next start, never over one that is there.

The fixture is scripts/fixture-repo.sh mono-web-api --listener, with two stand-in dev processes. The services line is detection at work: pando read the compose file and the env example, and chose. pando doctor says what it found and where.

When something fails

Note

If anything fails after the checkout, new undoes it. The worktree is removed, and so is the branch if this new created it. A new stopped by Ctrl-C during the checkout cleans up the same way.

A failed install is the exception: it keeps the worktree, and the next start tries the install again. Removing a worktree with rm always keeps its branch.

The main checkout

The main checkout runs too. It is always the first row, marked ⌂, and goes by its directory's name, or by its branch when no other worktree is on it: in a checkout of main, pando start main starts it, and so does pando start with no name from inside it.

The checkout is yours and you set it up, so pando runs its processes on ports it allocates and nothing else: no install, no hooks, and always on the project's own services. rm never removes it.

Careful

pando stop with no name, run from the main checkout or from outside any worktree, stops every worktree and the main checkout, not only the one you are in. Name it to stop only the main checkout, by its branch or its directory's name, such as pando stop main.

Worktrees you made yourself

pando manages every worktree git worktree list reports, so the ones you made by hand are listed, started and stopped too. They are marked adopted.

pando never writes into an adopted worktree, so the files provision names are not given to it. start and doctor say which it lacks, each with the command that supplies it.

Several repositories

A product split across repositories cloned side by side is one project. Run pando in the plain folder that holds them:

product/       a plain folder, not a repository
├── backend/   a git repository
└── frontend/  a git repository

Its worktree is a set, laid out like the folder. pando new feat/x makes <set>/backend and <set>/frontend, each a worktree of its own repository on feat/x. A repository that already has the branch, locally or on origin, uses it. One that does not forks a new branch from its own base.

One branch, one row, one port window

start runs every process of the set in one port window, so a process with cwd = "frontend" reaches the backend's port through {port:api}. Stopping, removing, status, opening, sharing and checking act on the whole set too.

The TUI shows a set as one row, with each repository's branch and changes in its detail. pando status lists each repository of a set, and pando logs --source backend reads the processes that run in it.

Choosing the repositories and their bases

Every repository directly under the folder is in the project. In the project's pando.toml, [repos] members narrows that, and [repos.base] gives one repository a base other than its own default. A [branches] rule that matches the branch still comes first.

[repos]
members = ["backend", "frontend"]
base = { backend = "develop" }

A path in config names its repository first: provision = ["backend/.env"].

Setup, and finding the project

pando init --agent, run from the folder, hands the setup to your coding agent as it does for one repository. Detection reads each repository as an app: its process, its install, its .env, a compose file at its root, and the port one app reaches another on.

A set that lacks a repository's checkout, lost or added since, gets it back from pando new on its branch. From inside a set, or one of its checkouts, pando finds the folder's project. From a repository's own main checkout, the project is that one repository, as before.

The git menu moves one checkout at a time. On a set it opens on the first repository's checkout, measured against that repository's base, and tab goes to the next.

Running

Detached, with no daemon

Every process runs as bash -lc '<cmd>' in a session of its own, which gives it its own process group and no terminal. Its input is /dev/null, and its output is appended to logs/<worktree>/<process>.log in pando's home. Close the terminal or quit the TUI, and it keeps running.

There is no pando daemon. What runs where is kept in state.json. Whenever something reads it, such as ls, status, the TUI or a start that waits, pando brings it up to date by scanning each process group: with ps and lsof on macOS, and /proc and ss on Linux.

Several processes

A worktree can run several processes, such as [processes.api] and [processes.web]. Each has its own command, directory, environment, ports, readiness and log.

--only web starts, stops or restarts one of them, and the others keep running on the ports they have.

Ready means listening

On a terminal, start waits until each process's own process group is listening on its port. The default limit is 30 seconds, and ready.timeout_s changes it. A process with no port has nothing to check, so it must stay up instead: five seconds, or its own ready.timeout_s up to ten.

This is a socket check, not an HTTP health check, and pando never binds the port itself to test it. When a process does not come up, you get the last lines of its log and the reason:

From a script or an agent, start and restart return as soon as everything is spawned. --wait makes them wait there too, and --no-wait makes them return at once on a terminal.

Stopping

stop sends SIGTERM to the whole process group, meaning the server and everything it forked. It waits up to five seconds, then sends SIGKILL. A backgrounded server whose parent already died is found and stopped too.

A stop also takes down the worktree's private services and public URL. Its ports, logs and data are kept.

What survives a closed terminal, or a reboot

Closing the terminal, killing the tmux pane or quitting the TUI leaves everything running: each process has its own session and no terminal.

A reboot stops them, as it stops anything. pando notices the new boot and forgets the old process ids, but it keeps each worktree's ports and mode, so the next start comes back on the same URLs. Nothing restarts by itself: there is no daemon and no supervisor.

Ports

Ports are chosen at start, and never at random. pando hashes the project id and the worktree's name into one of 1,971 windows of eight ports between 17000 and 32767. That range sits below the ephemeral ports that macOS (49152 and up) and Linux (32768 and up) hand out.

Each role takes the next port in its window. A role is a name like web, api or a private postgres. Processes come first, then services, so switching a worktree to isolated keeps its web port whenever the ports after it are free.

The ports are recorded, so a bookmarked URL keeps working across stops, restarts and reboots. They move when something else took one, and pando says so: the ports feat/login had were taken; it moved to new ones. Adding or removing a process, or switching to or from isolated, fits them again, usually on the same numbers.

Environment


pando never edits a .env, a framework config or a package.json to set a port. Ports and service addresses reach your app as environment variables, or as placeholders in its command. One process can learn another's port the same way.

Light on disk


You keep many worktrees, so what one costs is paid many times over. pando keeps that cost down, and measures what is left.



A copy-on-write checkout


Where the filesystem can clone (APFS on macOS; btrfs, XFS or bcachefs on Linux), pando new clones your main checkout's files into the new worktree. The clones share disk blocks until one of them changes, and git writes only the files that differ on the branch.


Example
Say your checkout is 300 MB across 4,000 files, and your branch changes 40 of them. A plain git worktree add writes all 300 MB again. pando writes those 40 files, about 3 MB, and clones the rest.


The result is the tree git's own checkout makes: the same files, modes and git state, made by git's own reset --hard. A file whose checkout converts it (CRLF endings, a filter, ident) is always written by git, and a post-checkout hook runs as usual.


A filesystem that cannot clone, such as ext4, keeps git's own checkout, and so do core.autocrlf, core.eol=crlf, a repository-wide attributes file, a sparse main checkout, and a git too old to read attributes from a commit. copy_on_write = false turns it off.


du still counts each worktree in full. The saving shows up as free space.



Dependencies, cloned


[project] clone lists gitignored paths, such as node_modules, that new clones from the main checkout before the install, so the install only fixes what differs. It is never a full copy: on a disk that cannot clone, they are left to the install.


pando proposes it for the node_modules your main checkout has, the root's and each app's, unless the install deletes them first, as npm ci does. clone = [] records that you want every worktree installed from nothing.


Never cloned, each with a line saying so: a path the install deletes first, a Python virtualenv (its scripts name main's interpreter by path), and a tree with a link out of the worktree. pando check never clones, so a check still proves the install works from nothing.



Rust builds, cloned


clone also takes a Rust crate's target, and pando proposes it beside a Cargo.toml. A new worktree then starts with the main checkout's build. Cargo's fingerprints for dependencies name no path of the checkout, so cargo finds every dependency fresh and builds only the workspace's own crates. A Maven or sbt target is left alone.



What a worktree costs: the check's report


Before it removes its worktree, a passing pando check measures what that worktree cost on disk:


    

  • Each gitignored tree the install and the processes left, a megabyte or more, twelve at most, marked when your main checkout has one clone could share.
    • 

  • What was written outside it, such as a build cache keyed by the checkout's path, which fills again for every worktree.
    • 




pando check --json carries the same numbers as disk:


"disk": {
  "trees": [
    { "path": "node_modules", "bytes": 480000000,
      "main_has": true, "cloned": false }
  ],
  "outside_bytes": 12000000   // null where it was not read
}


The outside figure is approximate: anything else that wrote meanwhile counts too, so check twice before acting on a surprise.



pando measures; your project decides


pando knows no ecosystem here. Which trees are safe to share, and which setting makes a cache independent of the checkout's path, is your project's call.


A tree is worth cloning when the tool that wrote it checks what it reuses, as a package manager or cargo does, and not when its files record the main checkout's path. A path-keyed cache usually has a setting of its own, given to the process through its env. Such a setting can change how a program behaves, so weigh it first.


The brief's "What a worktree costs on disk" walks your agent through both, and the setup report says what was shared. Check again after a change, and compare.







Sharing



Its local URL


Each worktree has one local URL, http://localhost:<port>, for its web role, or else for the first role that owns a port and serves a page. pando open opens it in your browser and prints it too, so it works over SSH. o opens it from the TUI, and c copies it.



A public URL


pando share feat/login publishes a running worktree through a cloudflared quick tunnel. It needs no account, and it prints one line: https://<random>.trycloudflare.com. In the TUI, t shares and asks first.


Every share gets a new random host. The link closes on unshare, stop, rm, and a restart of the whole worktree. restart --only keeps it.


Warning
Public means public. Anyone with the link reaches the app until you unshare, stop or remove the worktree. The link does not expire.



Apps that need a login


If your app needs a login, [share] auth_cmd runs a command in the worktree, and its output becomes a Cookie header. A small proxy, bound to 127.0.0.1, puts that header on every visitor's request in place of any cookies their browser sent.


The link then opens already logged in, as the same user for everyone. That logs visitors in. It does not keep anyone out.

From a fork


A pull request from a fork has no branch on origin, so pando fetches refs/pull/<n>/head into a branch of its own, pr-<n>/<branch>. A pull request from the same repository whose branch is gone from origin is refused, rather than started as an empty branch with the same name.



On the list


A worktree with an open pull request shows it as ◍ #n: ◌ for a draft, ✓ once merged, ✗ once closed. space p opens that pull request on GitHub.


pando asks GitHub again about once a minute, and when you come back to the pane, so a merge shows without a restart. The header names the account gh uses here.


Pull requests are in the TUI only for now, and need gh signed in.







The git menu


space g on a row reads where its branch stands and offers what can be done to it, with why not where it cannot. Each move shows the exact git commands first. ⏎ runs them, and esc always goes back one step.




f
Fetch.


p
Pull: fast-forward the branch to its upstream, and nothing else.


r
Rebase it onto its base.


m
Merge its base into it.


a
Abort a rebase or merge left half-done.


!
A shell in the checkout, to do it by hand.




A rebase or merge that stops on a conflict is aborted again before it is reported, so the checkout is exactly as it was. When the branch of a checkout that runs has moved, the menu offers to restart it.


The menu never pushes, resets, stashes or switches branches. On a checkout with uncommitted changes it only fetches; pull, rebase and merge wait until it is clean. On the main checkout it only fast-forwards. It moves a branch only when you pick the move and have seen its commands.







Three modes


In every mode, a worktree's code, processes, dependencies, ports and logs are its own. The mode decides one thing: which database and cache it talks to. You choose per worktree, and pando remembers: a plain start keeps the mode a worktree last ran in.



  
Shared Default
S · --shared
The main checkout's servers, and its data. Nothing starts and nothing waits, which is right for most changes.
Own: code, processes, ports, logs.
Main's: the database, the cache and their data.

  
Namespaced Experimental
⏎ then choose · --namespaced
A database, a Redis slot or a name prefix of its own, inside the servers your main checkout already runs. The branch's own schema step builds it, and main's data is never touched.
Own: all of the above, plus a database, a slot or a prefix.
Main's: the servers themselves.

  
Isolated
i · --isolated
Servers of its own, on ports of its own. They are the containers in your compose file, or native servers from a recipe if you would rather not run Docker.
Own: all of the above, plus every server and every byte of data.
Main's: nothing.





Choosing and switching


⏎ in the TUI opens the mode chooser on any worktree. On a stopped one, the mode it last ran in sits under the cursor, marked last used, so ⏎ ⏎ is still one quick start. A worktree never started has shared there.


On a running worktree, its mode is marked running, and choosing another switches it: every process restarts on the other services. i and S go straight to isolated and shared. The main checkout always runs shared. From the command line, start and restart take --isolated or --namespaced, and start --shared is the way back.



How the app finds its database


Through its environment, never by writing a file. For each variable the config maps to a service, such as DATABASE_URL = "postgres", pando reads the value your env files already have and changes only what the mode needs.




In shared mode, the worktree's processes get the main checkout's own values for the database and cache variables, read from its .env or env example.







Isolated



With your compose file


An isolated start runs your compose file under a compose project named for the worktree, so the containers, the network and the named volumes are separate for every worktree. A generated override, kept under ~/.pando, publishes each service on a port pando chose, bound to 127.0.0.1. Your compose file is never edited.


$ docker compose -p pando-shop-0b790793-feat-login-0499 \
    -f docker-compose.yml \
    -f ~/.pando/projects/shop-0b790793/compose/feat+login.override.yml \
    up -d postgres redis

Without Docker


A native service is a recipe: a TOML file that says which binaries it needs, how to start one server on a given port and data directory, and how to tell when it is ready. Four are built in: postgres, mariadb, redis, and mongodb, which is marked untested.


Each server gets ~/.pando/projects/<id>/data/<worktree>/<service>, is initialised once, and binds 127.0.0.1 only. The built-in servers have no passwords, since nothing off your machine can reach them. pando never installs an engine. If one is missing, it prints the install command.




Your own recipes


A file with the same name in ~/.pando/recipes/ replaces a built-in outright, for every project on the machine. A new file adds an engine. Which mechanism a machine prefers, compose or native, is [isolation] prefer in ~/.pando/config.toml.


Native Postgres and MariaDB put their socket in $TMPDIR/pando-…, because a socket path longer than 104 bytes does not work on macOS.







Namespaced


Namespaced mode is experimental. A namespaced start writes into a server that belongs to you, which pando's rule about your repository does not cover. So the mode is opt-in, and it has rules of its own.



The login


It logs in the way your app does, with the user and password beside the address in the main checkout's .env: the root's, or the one where a process runs, such as backend/.env.


Where there are none, a server in a container is reached as its own administrator. Anywhere else, pando asks once, keeps the answer in its own config for the project (mode 0600), and hands it to the database client in its environment, never on a command line.



The grant


That login must be allowed to make databases named after the main one. The first start that is not allowed stops with nothing made, and prints the statement to run once as an administrator. On MariaDB and MySQL it covers those names and nothing else:


mariadb on localhost:3306 does not let the login from the URL in
DATABASE_URL make or drop shop__feat_login — run this once as an
administrator of that server:
 
    GRANT ALL ON `shop\_\_%`.* TO 'app'@'localhost';
 
It lets that login make and drop databases named shop__… and
nothing else. Nothing was made.


Postgres cannot grant by name, so there it is ALTER ROLE "app" CREATEDB;, and the role can drop only the databases it owns, which are the ones it made. The official image's POSTGRES_USER needs neither.


The database is made in main's encoding and locale. It starts empty and is built by the branch's own schema step, never copied from main's.



Servers in containers


A server in a container needs neither the grant nor a question. Its environment keeps its administrator, such as POSTGRES_USER or MARIADB_ROOT_PASSWORD, so pando runs the statement itself as that administrator, and the database is made as the app's login, which owns it. Where the app has no login at all, the administrator is the login.


A database in Docker usually leaves the host with no client. Then the commands run through docker exec in the one container that publishes the server's port on this machine's loopback, with the client its image ships and the password passed by name. A server elsewhere, or a native one on the same port, is never taken for it.



Redis slots


A Redis slot is given out only where the app reads a slot setting, such as REDIS_DB or the path of its URL, and only while the slot is empty: keys pando did not put there are someone else's. Slot 0 and main's own slots are never given out.


When all fifteen are held, the start asks which stopped worktree gives its slot up, and only a person may answer.



Prefixes for search, queue and cache engines


Some servers have no namespace pando could make: an Elasticsearch index, a Kafka topic or a Memcached key belongs to the app. There, a worktree is told a prefix of its own in the key its app already reads one from, such as ELASTICSEARCH_INDEX_PREFIX=feat_x_1f3c4a__, with main's own prefix first when it has one. pando makes nothing there, so it records and drops nothing, and rm says what it leaves.



What it drops, and what it never does


Every drop goes through one check. A record must say pando made that database for that worktree, on that server. The name must never be main's, must carry the __ marker, and must not be named by any other record. pando doctor lists a leftover with the command that drops it, and never drops it itself.



When pando cannot tell


What pando cannot tell by itself is written in its own config for the project, under [namespaced.<service>], usually by the setup agent through pando init --answers. None of these keys is a secret, so a committed pando.toml may carry them too. A login, user and password, is read from pando's own file only.


[namespaced.redis]
db_env = ["REDIS_DB"]          # one REDIS_DB that three Redis roles share

[namespaced.search]
recipe = "elasticsearch"       # an image whose name says nothing
prefix_env = ["SEARCH_INDEX_PREFIX"]


pando signals lists what a namespaced start would do with each service, and why one stays shared. pando init names the services it would leave on main's data.

An engine pando does not ship


What a namespace is on an engine is data: a recipe's [namespace] or [prefix] table, so another engine is a file in ~/.pando/recipes/ rather than a release. A compose image finds it by its own name, or by [namespaced.<service>] recipe. It needs no [service] table when pando never starts the engine.



Each command keeps a contract: create fails when the name exists, a slot's commands never fall back to slot 0, size prints a bare number, and the password reaches the client only through password_env.


pando derives every name, <main>__<worktree>, and drops only what its records say it made. An engine whose namespaces are the app's own convention needs only a [prefix] table.

Taking the first choice


On a terminal, new, start and the TUI take the rules' first choice for anything they have one for, and print what they took, with the file they wrote it to:


pando: process list: using "npm run dev" (package.json scripts.dev, which starts the workspace's apps itself; API_PORT and WEB_PORT in the env example), pando's first choice, over 1 other option — change it in ~/.pando/projects/<id>/pando.toml


A question pando has no option for at all is still asked. So is the one real choice isolation brings: which services get private copies. From a script or an agent with no --yes, such a question exits with code 3 (see For agents).



Answering in one pass


pando init puts every open question to you in one pass, instead of taking defaults as you go. A second run asks nothing. pando init --yes takes pando's own recommendation for each.


A program answers through pando init --answers -: one JSON object on stdin, keyed by the question's name. --dry-run prints the file it would write and writes nothing, and --replace changes an answer that is already there:


$echo '{"clone": ["node_modules"]}' | pando init --answers - --replace


pando doctor says what was detected, from where, and what is missing. pando signals prints the evidence as JSON.







pando.toml


The answers go to ~/.pando/projects/<id>/pando.toml, with file mode 0600, never into your repository. You never have to write one. pando writes it, and each line it writes carries its reason.



The file is yours to edit. pando adds keys that are missing, and changes an answer only when asked to, with init --answers - --replace. Delete a line and run pando init, and that question is put to you again.



Layers


Config comes in layers, highest first: pando's own project file, then the machine-wide ~/.pando/config.toml. For now, a pando.toml committed in the repository is read beneath them and never written. Whether to honour one is still an open decision.

pando check


pando check proves a setup in a throwaway worktree. It makes a detached worktree of the commit a new branch would fork from, so there is no branch. It installs it, starts every process, waits until they are ready, and asks the process that owns the URL for /.


Then it stops and removes the worktree, keeps its logs, and records the result in check.json. In the TUI, v runs it.




What passes


A status of 500 or higher, a refused connection or silence is a failure. Any other answer passes: a login redirect is a working app.


The exit code is 0 when it passed, 1 when it failed, and 3 when a question is still open. --json prints the result as one object, and its kind says whose a failure is: the settings', this machine's, or the base commit's.



What it never touches


The check runs on the shared services and skips the hooks that run after the services or after dev, so it never migrates your own data. Everything it runs gets PANDO_CHECK=1.


When the project has a schema step to prove, and a namespaced login already exists or a container's administrator gives one, the check proves that step in a namespace of its own, and drops it with the worktree.


A passing check also measures what the worktree cost on disk before it removes it: see the check's report. --base <branch> tests the commit that branch is at, for this run only.

Remembering the project


pando init --agent --reference memory prints a short block on how to run this project's worktrees with pando. The setup agent offers to save it in its own memory, and does so only when you say yes, so later sessions start and stop worktrees through pando rather than by hand.


pando also keeps the block as CLAUDE.md and AGENTS.md in the project's directory under ~/.pando, above every worktree, never in your repository.







Commands


A worktree is named by its branch (feat/login) or its directory (feat+login), and inside a worktree most commands need no name (see Names). stdout carries only the answer, and the narration goes to stderr.



Several at once


start, stop, restart and rm take several names, as in pando rm feat/a feat/b fix/c. They act on them side by side and say each one as it finishes. One that fails leaves the others to finish, and the exit code is then 1.


A start of several settles every question first, one name after another, and then starts them all. If a question is still open, the whole command exits 3 and nothing is started. Every flag applies to each name.

Confirmations


A key that would interrupt a running worktree asks for a second press within three seconds. x x stops it, r r restarts it, and P P restarts one process. i or S twice restarts it in the mode it already runs in. esc takes the first press back. On a worktree with nothing up, stopped or failed, the first press acts.


Sharing, removing and stopping everything always ask in a dialog, and so does moving a running worktree to another mode.


x on a worktree being started cancels the start: it stops at its next safe point, undoes what it brought up, and the worktree ends stopped. q q with a start in flight does the same, then quits.



Marks: several rows at once


+ marks the row under the cursor, or unmarks it, and moves down. esc unmarks every row. A mark stays on its worktree through a refresh, a re-sort or a filter.


While rows are marked, s, x, r and d act on all of them at once, and x x or r r asks once for the set. d opens one dialog that says what each removal takes with it, which only F removes (uncommitted changes), and which stay. Every other key acts on the row under the cursor.

While pando has the mouse, hold shift to select text (option in iTerm2). [ui] mouse = false in ~/.pando/config.toml leaves the mouse to the terminal. The setup screen always does, so its prompt can be selected and pasted.



Sorting the list


The main checkout is always the first row, and the worktrees with something up come right after it: a start moves a row up, and a stop puts it back. , changes the order within each group: by pull request, highest first (the default), newest first, last run first, or by name. The choice is saved as [ui] sort.



How it keeps up


The screen keeps up by polling: processes every second, the worktree list and the selected row's git state every five seconds, the other rows' git state every thirty, and GitHub about once a minute. A watcher on the worktrees directory reads the list again as soon as a worktree appears or goes, and coming back to the pane reads the list, git and pull requests again. It fits a tmux split: below 72 columns, the table and the detail pane stack.

Machine config and themes


~/.pando/config.toml holds what belongs to the machine rather than to a project: the runtime prelude, which isolation to prefer, and how the TUI looks and behaves.




Themes


T in the TUI lists the colour themes, each with a swatch of its colours. Moving through them repaints the screen, ⏎ keeps one, and esc puts the old one back.


Fifteen are built in: pando's own, Catppuccin, Flexoki, four GitHub themes (default, dimmed, high contrast and colorblind), Gruvbox, Kanagawa, Monokai Pro, One Dark, Rosé Pine, Tokyo Night, VS Code and Zenwritten. Each has a dark and a light half that follows the system.


theme_from names a file whose first line is a theme's name, such as the state file a terminal theme switcher keeps. pando follows it while it runs, so switching the terminal's theme switches pando's with it. PANDO_THEME and PANDO_APPEARANCE override both for one run.


A theme is a small TOML file: for each half, a background, a foreground and seven accents, and optional keys such as surface or border for a colour you would rather set than derive. Every colour left out is derived from the others. A file in ~/.pando/themes/<name>.toml is listed beside the built-ins, and replaces the built-in of the same name.



pando's home


Everything pando keeps lives under ~/.pando. Set PANDO_HOME to move it elsewhere.







The two promises


These two rules come before every feature.



pando never writes into your repository


Not a config file, not a gitignore line, not a lockfile change. Apart from a socket directory in $TMPDIR for native Postgres and MariaDB, pando's own files go to two places:


    

  1. its own home, ~/.pando/;
    2. 

  2. the worktrees it creates, which live under that home by default.
    3. 



Inside .git, only git itself writes: its records of the worktrees, branches and fetches pando asks for. pando writes no file in your checkout; only the git menu, when you pick a move, has git move a branch.


Inside a worktree, pando may create or link a file only if the project's own gitignore already ignores that path. .env and .env.local pass. Anything that would show up as untracked in git status is refused.




How it is kept


    

  1. Every path is computed. Every location pando writes is a function of its home and a project id, and a test checks that none of them is inside the repository. A home or a worktrees_dir inside the checkout is refused before anything is made.
    2. 

  2. git check-ignore runs before every write into a worktree. It runs in the main checkout first, then again inside the new worktree right before each file is written, because a branch can carry an older gitignore. A refusal found after the worktree was made undoes it.
    3. 

  3. Hooks and installs are watched. git status is taken before and after them, and pando warns about anything new that appeared.
    4. 

  4. Every command is checked by a test. After each one, the test suite checks that git status has nothing to report, and that every path in the repository outside .git has the same type, size and symlink target as before.
    5. 




What it does and does not cover


Git itself records worktree admin files in .git/worktrees, and new branches and fetched refs in .git. A worktree gets the gitignored files you listed linked into it, and its own dependencies installed, such as node_modules. The worktree itself lives under ~/.pando. Nothing pando writes shows up in your checkout's git status.


Three things fall outside the rule as written, by design, and each has rules of its own:


    

  • Namespaced mode, when you choose it, makes databases in your own server. Each is named after your main database, so it can never be it, and only rm drops it, only when pando's records say pando made it. See Namespaced.
    • 

  • The git menu moves a branch in a checkout, but only the move you picked, after you saw its commands. See The git menu.
    • 

  • The copy-on-write checkout clones the branch's own tracked files into a new worktree, as git worktree add would write them, and git's own reset decides what each one holds. See Light on disk.
    • 




No AI at runtime


Discovery may be fuzzy. Starting processes may not. Detection is the only thing that writes pando.toml, whether init runs it, or new, start and the TUI ask it as they go. Spawning, stopping, sharing and removing only ever read it.


So a wrong guess costs one edit to a file you can see. It never costs a mysterious failure at start time.


There is no model SDK and no HTTP library in the binary. pando itself talks only to this machine. What reaches the network are the programs it runs: git, gh, cloudflared, docker, your install and hook commands, in namespaced mode the database clients, and for pando update, curl and brew or cargo. There is no telemetry, and you need no account.







Questions




How is this different from plain git worktree?

git worktree add ../x feat/x gives you a second checkout and nothing else. pando new feat/x makes the same kind of worktree, but under ~/.pando instead of beside your repository, and where the disk can clone, as a copy-on-write clone of your main checkout that git then brings to the branch. It links in the gitignored files the project needs, runs the project's own install inside the checkout, and records it.


pando start then adds what makes it run: ports that do not collide, detached processes, logs and readiness. Optionally it adds private or namespaced services and a public URL, all on one screen. Worktrees you made by hand are managed too.


Does every worktree get its own node_modules? Its own .env?

It gets its own dependencies. pando runs the project's frozen install inside each worktree and never links dependency directories. With clone = ["node_modules"], which pando proposes when your main checkout has them, the main checkout's are cloned in first, copy-on-write: each worktree's own copy, sharing disk blocks until it changes.


A later start runs the install again only when a lockfile, a version file or the prelude changed.


Local config works differently. Gitignored files like .env are symlinked to the main checkout's copy by default, so editing one edits main's. provision_mode = "copy" gives each worktree its own copy.


What survives closing the terminal? A reboot?

Closing the terminal or quitting the TUI leaves everything running. A reboot stops it all, and the next start comes back on the same URLs. Nothing restarts by itself: see Running.


My Node from nvm (or fnm, rvm…) is not found.

pando starts commands with bash -lc, a login bash, which reads ~/.bash_profile and never ~/.zshrc. A version manager set up only in .zshrc does not exist there.


pando doctor shows which binary each language resolved to. The fix is a one-line [runtime] prelude for your machine, kept in ~/.pando/config.toml rather than in the repository.


I moved my repository and pando forgot it.

A project's pando data is keyed by the folder's name and a hash of its path, so after a move pando sees a new project. pando doctor finds the old one, and pando doctor --adopt <old-id> moves its config, state and worktrees over.


Does pando new fetch the newest base first?

No. A new branch forks from the last-fetched origin/<base>, so run git fetch first when you need the newest commit. An existing branch is looked for locally, then on origin.


How many worktrees can run at once?

As many as your machine can run. Every running worktree runs its own dev servers, and in isolated mode its own databases too. The ceilings in the code are 1,971 port windows, and 15 Redis slots per Redis server for namespaced worktrees. The TUI is built for dozens of rows.


Is a share link private?

No. Anyone with the link reaches the app until you unshare, stop or remove the worktree, and with auth_cmd every visitor gets the same session. See Sharing.


Logged in on one worktree, logged in on all of them?

Browsers keep cookies per host, not per port, so every http://localhost:<port> shares them. That is how the web works, and pando does not change it. When two branches' sessions get in each other's way, use a private window for one of them.


Linux? Windows?

macOS is where pando is developed. Linux passes the whole test suite on every change, but nobody has used it there for real work yet. On Windows, run it inside WSL 2, with the repository under ~. See Platforms.


Does pando use AI, or phone home?

No and no. Detection is rules and data tables, and the runtime never calls a model. The agent in the first run is your own coding agent, which pando never launches: the setup screen only copies a prompt for you to paste.


There is no telemetry in the code. pando itself connects only to this machine: pando check asks your app for / on localhost, and the share proxy forwards to it. The network is reached only by the programs it runs (see No AI at runtime).









Where it stands


pando is pre-release. What changed in each version is in the changelog.



What there is


    

  • Every command on this page is implemented and covered by tests.
    • 

  • The tests read no developer's shell profile and need none of their tools. The databases in the tests are throwaway servers the tests start themselves.
    • 

  • pando is developed on macOS. For every change, CI checks formatting, runs clippy and the whole test suite on macOS and on Linux, and runs clippy for a native Windows build. All of it must pass.
    • 

  • Binaries for macOS and Linux, the install script and the Homebrew tap ship with every release.
    • 




What there is not, yet


    

  • There is no crate on crates.io yet.
    • 

  • Nobody has used pando on Linux for real work yet: the suite that passes there runs on fixtures. Under WSL 2 the suite passes too, and fixture worktrees have run there, but no real project yet. On Windows, pando runs inside WSL 2, not natively.
    • 

  • pando has met only a handful of real projects: the monorepo it was built for, where it is used daily, and the apps of the people who opened its first issues. Each found something no fixture had, and all of it is fixed.
    • 

  • Namespaced mode is experimental. Its container path is tested with a stand-in Docker in front of real servers, not yet in a real container, and the prefix engines on fixtures alone.
    • 



Note
A tool this heavily tested against situations it invented still breaks on first contact with one it did not. If pando breaks on your project, that is the most useful issue you can open. Open an issue.



What is next


Roughly in order: a published crate, a JSON schema for pando.toml, and a recipe directory with its own contribution guide.
